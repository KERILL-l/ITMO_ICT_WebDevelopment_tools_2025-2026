ЛР2 — Потоки, процессы и асинхронность

Во второй работе сравниваются три способа делать несколько дел одновременно: потоки, процессы и async. Для проверки использовались две задачи: сумма чисел и парсинг веб-страниц.

Что проверяется

В какой задаче какой подход работает лучше и где он дает меньше задержек.

Что используется

Результаты парсинга пишутся в ту же PostgreSQL-базу, что и в первой лабораторной.

Технологический стек

Компонент Используется Назначение

ПроцессыmultiprocessingНастоящий параллелизм для CPU-bound задач
Asyncasyncio, aiohttpНеблокирующие HTTP-запросы и event loop
ПарсингBeautifulSoupИзвлечение заголовков HTML-страниц

Задача 1 — сумма чисел

Потоки

Делят один процесс и один словарь результатов. Для этой задачи работают, но не всегда дают большой выигрыш.

Процессы

Каждый процесс работает отдельно. Это полезно, когда задача тяжелая и нужна настоящая параллельность.

def calculate_sum(start: int, end: int) -> int: return sum(range(start, end + 1)) async def main_async(n: int = N_DEMO) -> float: with ProcessPoolExecutor(max_workers=NUM_WORKERS) as executor: partial_sums = await asyncio.gather(*tasks)

Задача 2 — параллельный парсинг

Потоки

Подходят, когда программа ждет сеть. Пока один запрос ждет ответ, другие могут работать.

Async

Самый удобный вариант для большого числа запросов. Один цикл событий управляет всеми загрузками.

Подход Что делает Итог
Threadingrequests + BeautifulSoup + запись в БДХорош для сетевого I/O
MultiprocessingОтдельный процесс на URLИзбыточен для I/O, но изолирован
Asyncaiohttp + asyncio.gatherЛучший вариант для массовых запросов

Выводы

Сумма чисел

В этом запуске быстрее всего оказался threading: 0.0758 сек. Multiprocessing дал 0.0860 сек, а Async + ProcessPoolExecutor — 0.0780 сек. Разница небольшая, поэтому все три варианта работают почти одинаково.

Парсинг страниц

Здесь быстрее всего оказался async: 0.6599 сек. Threading показал 0.8141 сек, но у него был один сбой из-за повторной записи parser_bot в БД, поэтому результат нужно смотреть с оговоркой.

Общий итог

Для вычислений подходит любой вариант, если задача небольшая. Для загрузки страниц лучше async: он быстрее и проще для большого числа запросов.

Короткий вывод: для первой задачи разница между подходами почти не заметна, а для парсинга страниц лучше всего подошел async. Threading тоже работает, но в моем запуске один запрос упал из-за одинакового пользователя в базе.

ЛР3 — Docker, парсер и Celery

Третья работа объединяет API из ЛР1, парсер-сервис, Redis и Celery. В результате получается многоконтейнерная система, которую можно запускать через docker-compose.

Подзадача 1

Упаковка API и парсера в Docker, запуск через compose, работа с общей БД.

Подзадача 3

Очередь Celery + Redis для фонового выполнения парсинга без блокировки клиента.

Парсер-сервис
